## Minimal API proposal for coordinator/F review

No shared model fields or new dependencies are required for the initial implementation. A concrete `copy_with_recovery` function owns the first production COPY attempt and any safe retries; it does not accept a caller-manufactured first error. Inputs: mutable TargetConnection, TablePlan, borrowed EncodedBatch, stop/reject policy, real RunArtifacts, a shared per-run RejectBudget, and a synchronous progress observer. Keep these domain inputs in one small context struct if necessary for interface clarity; no generic source/target driver abstraction or fake persistence path.

`RecoveryProgress` supplies cumulative committed/rejected rows **within this immutable batch**, active submitted subrange rows and remaining pending rows. Observer runs immediately before every awaited COPY attempt and immediately after each acknowledgement/durable rejection. F applies deltas to its TableReport and publishes active inflight rows before awaiting; successful subranges cannot be lost if a later range fails or the future is canceled. A returned RecoveryError contains the last progress snapshot, sanitized target failure when present and a finite stop reason (database, reject I/O, reject limit, observer I/O, invalid batch or retry exhaustion). A recovery success with rejected rows is Partial, not Complete/exit0.

The shared RejectBudget enforces the configured **global run limit** for conversion and server rejects. Reserve a slot before writing; only durable writer success becomes a rejected row. Exact-limit completion is allowed; the next bad row stops without exceeding the durable cap. Conversion integration must use the same budget and existing reject_conversion API. This must remain safe under T13 workers; use an atomic claim/ticket whose unsuccessful persistence does not increment the reported durable reject count.

Use a fixed, documented maximum of3 transaction attempts per range with bounded20ms/40ms backoff for initial T12; no new undocumented TOML option. Observer/cancellation failure stops further submissions. F's existing global cancellation path remains responsible for socket cancellation and joining tasks; a dropped recovery future never continues in a spawned detached retry.

## Safety and ownership invariants

1. Validate offsets once: each row must be nonempty, within storage, contiguous, end in LF and have an increasing valid source ordinal. Empty batches return zero without recovery work. Generated SQL/column-count/configuration failures never become arbitrary row rejects.
2. Keep one borrowed immutable EncodedBatch and its Arc<BatchStorage>/OwnedSemaphorePermit throughout recovery. Select `Bytes::slice` between original row offsets and retain ranges as integer indices; do not clone EncodedBatch.rows or allocate copied sub-buffers/new full-batch permits. Depth-first right-then-left stack processing yields left-to-right order, with O(log row_count) range metadata and bounded memory. UTF8 expansion/bytea data remain exact encoded bytes.
3. Every attempt uses normal BEGIN→COPY→finish/count-check→COMMIT via the real PostgreSQL helper. Only acknowledged rows count committed. Failed row attempts are rolled back before subdivision. Leftmost good ranges commit before later conflicting rows, giving deterministic first-wins behavior for a fixed ordered input and exclusive destination.
4. Initial allowlist remains the production transport's reviewed `22001,22003,22007,22008,22021,22P02,23502,23505,23514`, only at CopyData/CopyFinish, with no cleanup cause and target stage Idle after the helper's explicit successful rollback. RowData cannot arise from Begin/CopyInit/CommitAttempt in the current helper. Deferred/foreign-key/exclusion/trigger-wide failures are fatal until a stronger row-local contract exists. A sole surviving row is written exactly once through reject_copy with original locator, exact COPY bytes and a static SQLSTATE reason; no raw server DETAIL/CONTEXT goes to logs.
5. Only `40001`/`40P01` with confirmed successful rollback (CopyData/CopyFinish or a known-aborted CommitAttempt returning Idle) may retry the identical range. A Begin error has no explicit rollback proof in the current helper, so it is fatal rather than assumed retryable. `40003`, class08/protocol/connection errors, failed rollback, unknown code, init/permissions/missing table and any indeterminate COMMIT stop without bisection/replay.
6. Reject writer already flushes/syncs COPY data **before** sync'd metadata and poisons itself after any failure. Increment rejected counters only after that API returns success; dangling durable data without durable metadata is not a safely recorded rejection. Earlier acknowledged commits and durable rejects survive later failures; pending rows stay unresolved, and only the active sent range can become indeterminate.

## Existing contract gaps requiring coordinator decisions

- **Accounting integration:** current F commit_batch publishes the whole batch as inflight and increments committed rows only after whole-batch success. It must consume per-subrange progress; otherwise cancellation after one recovery commit double-counts those rows as indeterminate or loses acknowledged rows. This is a required executor change, not a shared-model addition.
- **Confirmed rollback API:** current production helper provides the required proof by returning original RowData/TransactionRetry only after observed rollback and setting Idle; recovery can audit that invariant without a new field. If transport APIs will be expanded or other callers can supply failures, introduce an explicit immutable rollback disposition rather than guessing from SQLSTATE. Begin TransactionRetry currently has no such proof and will not be retried.
- **Target side effects:** active user triggers or volatile/custom CHECK functions can raise an allowed SQLSTATE or perform nontransactional work. SQLSTATE/stage alone cannot make them safe to replay. Reject mode should preflight incompatible target behavior (and repeat after supported before hooks), or explicitly reject such cases until T11/T17 catalog contracts prove safety. A proposed minimal metadata addition is enabled-user-trigger inventory; existing TargetCatalog lacks it. Do not silently claim arbitrary target-trigger recovery support.
- **Permit lifetime:** Bytes driver clones do not themselves carry BatchStorage's permit. Retain the original storage until COPY finishes/rollback resolves; cancellation must stop admission and join/drop the protocol task before promising all retained driver aliases are released. Application byte budget remains separate from documented driver/RSS scratch/caches.
- **Conversion wiring:** F currently rejects reject mode before target mutation and stops on converter errors. Root/F must remove that gate only after server recovery and durable raw conversion rejects share the limit/progress contract. Recovery module alone cannot claim an end-to-end reject feature.

## Independent fault/acceptance checklist

- [x] First/middle/last/multiple/all/single bad rows: independent expected target rows/reject ordinals and exact bytes, deterministic repeats into fresh targets, good rows committed once.
- [x] NULL/empty/`\\N`, arbitrary bytea, Unicode/embedded COPY escapes: exact retained slice offsets and reject data; no re-encoding or content mutation.
- [x] Duplicate keys both within a batch and against an earlier committed batch: leftmost ordered survivor, later conflict durable once; unrelated valid rows remain.
- [x] CHECK/NOTNULL/length/numeric/input errors cover real approved codes; context is never parsed. Foreign-key/deferred/custom-trigger failures are fatal in real cases; exclusion remains outside the allowlist.
- [x] Stop policy: failing batch rolls back, no rejects, earlier committed batch retained, all uncommitted rows unresolved.
- [ ] Exact global reject limit and next-bad-row failure across multiple batches/tables/conversion+COPY paths; no extra record or double counter.
- [ ] Real artifact initialization/write/sync failures with the production writer; durable reject count is never advanced after failure, poison is surfaced, useful partial target/artifacts retained. Disk-full stage needs a concrete scoped fixture, not a successful skip.
- [x] Actual confirmed deadlock/serialization abort: bounded retry/backoff with identical bytes and no double commits; repeated deadlock exhausts the bound. Direct real COPY observes40001 independently before recovery replays the same scenario; no synthetic SQLSTATE is claimed as transaction proof.
- [x] COPY init/permission/missing table/column and malformed offsets/generated shape: no subdivision and no reject artifacts; actual startup codes and failed cleanup are retained safely.
- [ ] Connection loss before/during COPY and failed rollback: stop without replay. After COMMIT sent/lost acknowledgement: only active range indeterminate, earlier committed/rejected ranges preserved, never automatic replay.
- [ ] Cancellation at backoff, before splitting, after a committed left range, and during a right-range COMMIT: no new submissions, correct partial counters and bounded task shutdown.
- [x] Minimum byte-budget semaphore: available permits do not increase while immutable storage is retained across retry/split; aliases share storage and no new row-offset Vec copies; permits release after terminal cleanup.
- [ ] Full F CLI path: raw conversion reject+server reject records durable, partial exit3 unless stronger failure, report exact accounting and private artifacts; parent registers tests and fresh lanes fail on missing prerequisites.
