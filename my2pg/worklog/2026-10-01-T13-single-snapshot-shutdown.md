Primary sources read:

- [MySQL 8.4 KILL](https://dev.mysql.com/doc/refman/8.4/en/kill.html): KILL CONNECTION interrupts and closes a thread, own-thread termination needs no CONNECTION_ADMIN; statement success precedes completion. Native disappearance must be observed separately.
- [MySQL 8.4 metadata locking](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html): transaction-held metadata locks persist until transaction end. Client drop is not itself an observed transaction/server end.
- [MySQL 8.4 system variables](https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_lock_wait_timeout): lock_wait_timeout is session-scoped and bounds **each** metadata-lock acquisition; multiple attempts may exceed it. Default is one year. max_execution_time is a read-only SELECT execution timeout; this does not prove all metadata/catalog/cleanup waits are covered.
- [MySQL command phase](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_command_phase.html) and [COM_PROCESS_KILL](https://dev.mysql.com/doc/dev/mysql-server/8.0.45/page_protocol_com_process_kill.html): process kill is an ordinary command, deprecated in favor of SQL KILL. It does not supply an out-of-band interrupt on an already executing serialized command stream. The attempted latest COM_PROCESS_KILL documentation URL returned404; the documented8.0.45 page is used only for protocol shape, not a claim of an8.4 supported cancellation API.
- [MySQL consistent reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html): snapshot visibility belongs to the original transaction. Any replacement reader would change the consistency contract.

## Feasibility and smallest next experiment

There is no existing idle control socket in SingleSnapshot. A busy driver connection cannot send independent KILL through its ordinary command API without waiting for clean_dirty. Dropping the connection/future only establishes bounded client ownership cleanup. Reconnecting after that drop may temporarily retain the old server backend plus a new control backend; calling that a one-connection solution would hide a peak-budget increase and an ID-lifetime race.

**A one-socket MDL-specific candidate exists, but is not yet a complete shutdown guarantee:** set and verify a small internal `SESSION lock_wait_timeout` on the original source before starting the snapshot. Proposed focused development experiment uses1second, never a global variable, without changing the snapshot/reader/connection count. Cancel the run while its own table SELECT waits on an external owned metadata lock; drop the original socket, keep the lock held, and independently observe that exact server thread disappearing before the shared10second deadline. A negative control with the default timeout must remain visible until the lock is released or explicitly killed by the test owner. This proves timeout-assisted cleanup for that actual locked statement, not client drop alone.

Changing session policy is a reviewed transport choice: do not silently introduce a new arbitrary config option or alter the user whitelist in this research lease. It makes sufficiently long metadata-lock waits fail during normal operation; that consequence must be documented and SQLSTATE/code preserved. A finite retry of a cancelled SELECT would replace/reuse a damaged snapshot and is forbidden. Cancellation retains acknowledged target prefixes; a real timeout before cancellation remains SOURCE_READ/execution failure. No source table or global lock mutation is needed.

The primary documentation's per-lock caveat prevents deriving a uniform10second bound for every catalog/view/generated-expression/verification path from1second alone. Future views/hooks must not inherit this unproved claim. max_execution_time, wait_timeout, net_read_timeout/net_write_timeout, raw COM_QUIT and deprecated COM_PROCESS_KILL do not provide demonstrated universal cancellation while preserving current semantics. Do not close full T13 merely because the simplest MDL experiment passes.

**If a general independently interruptible source is required, the concrete minimal seam is an explicitly reviewed KILL-only control connection.** Keep exactly one original snapshot reader and transaction; create one separate verified-TLS source control guard before any target mutation, never use it for catalog/data/content reads, no pool/replacement reader. Hold the original reader/registered ID alive until KILL is issued and acknowledgement/disappearance checked; never target a stale ID after normal close. Own-user processlist inspection can confirm only that run's exact ID; no production scan of unrelated clients or extra privilege is needed. Dispatch cancellation with existing target requests under the same deadline, then close both guards. On control failure, fail conservatively and preserve pending source-cleanup evidence.

That seam changes the **current exact socket contract**, so it is a proposal for coordinator approval, not an implementation exception: SingleSnapshot normal reader=1 plus control=1 (or an explicitly reserved emergency source socket with peak_source=2). Source `ConnectionBounds`, report diagnostic, resource/unit/native oracles and architecture wording must all describe2server/client sockets where overlap exists. A cancellation-only freshly authenticated connection has greater failure exposure and cannot certify cleanup when auth/network is unavailable. A pre-opened control is simpler and observable, but cannot be silently counted outside the budget. If the coordinator retains one total source socket, retain the general server-cleanup gate as open instead of redefining it.
