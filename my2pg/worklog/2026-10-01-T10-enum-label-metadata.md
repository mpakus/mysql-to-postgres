## Implemented safe capability boundary

LOSSY_LABEL_METADATA is an error before cast resolution/ordinal construction. Root review tightened unknown metadata: '?' is accepted only with positive source BMP-only charset proof utf8/utf8mb3/ascii/latin1. Original column charset takes precedence over original table fallback; missing/unknown charset fails conservatively. Labels without? retain the existing capability policy. This intentionally refuses legitimate? labels in supplementary/unknown charsets because release-server catalogs cannot distinguish them from substituted codepoints. Other unproved charset/? combinations also refuse; no optional cast, charset replacement or ineffective omit can claim recovery. Actual column omission remains unsupported.

The direct tagged-source reason is server-side conversion before result encoding, not client decoding. Native protocol default buffers and observed data preserve individual values but never prove the complete unused ordered domain. No lossless ordinary SQL/column-protocol route was found on release MySQL8.4.11. Debug dictionary, filesystem SDI or full binlog metadata would be new capabilities/privilege/lifecycle contracts and are not silently required or used. Guard prevents data corruption while exact recovery remains a documented limitation.
