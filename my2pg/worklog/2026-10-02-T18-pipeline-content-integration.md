## Chosen integration contract

Wire Content only after the verifier exposes a sound API. Preserve the source snapshot already opened for SingleSnapshot; for Frozen consistency, use an explicit read-only source snapshot during verification under the operator's existing frozen-source guarantee. Scan PostgreSQL through one read-only REPEATABLE READ transaction. Pass `memory_bytes` and `max_row_bytes` into verifier-owned bounded streaming/spill logic. For Append, capture the exact target multiset before any DDL or COPY, keep its private spill-backed baseline alive until verification, and compare baseline plus migrated source rows to the post-run target. A count-only baseline cannot satisfy this contract. SchemaOnly and runs with rejected/incomplete rows must not report complete content equality. Unsupported canonical types and any source/target scan, disk, cleanup, or transaction failure must prevent a successful verification result.

The pipeline-level acceptance will include a successful equal-content run, same-count target corruption detected as Different, append with pre-existing duplicate rows and correct multiplicity, and an explicit unsupported conversion/type case. Test expectations must be independently constructed. Do not enable Content merely by removing the current early preflight refusal.

## Follow-up research for report-mode correction

The first owned MySQL 8.4/PostgreSQL 16 run reached the new runner case and stopped on an assertion: `RunReport.verification.mode` was `CountsAndSchema` although content scanning and the row assertion had completed. Before correcting this, XERJ `project-my2pg` query `VerificationReport mode counts_and_schema Content mode report labeling` returned `src/verify/mod.rs::counts_and_schema` and `src/pipeline/mod.rs` report initialization at indexed revision `db28c459a8a3caf45b07e9e72bcbc9fd3194c762`. The verifier initializes its report mode directly from the supplied plan; the coordinator passes a cloned plan with `CountsAndSchema` only to reuse schema/count checks. The T18 contract requires the final report to reflect the requested scope. Adaptation: restore the original Content mode on the combined report before publishing; the focused and full runner cases verify both in-memory and persisted mode. The failed harness stopped and cleaned up its DBs; its log remains under `target/integration/my2pg-mysql84-pg16-ddc1e16358be/`.

The next focused attempt passed the full Content runner and confirmed `verification.mode=content` in its emitted report, then Append preflight rejected the hand-built target as `TARGET_COLUMN_INCOMPATIBLE`. XERJ `project-my2pg` query `TARGET_COLUMN_INCOMPATIBLE append target varchar type compatibility` returned `src/plan/existing.rs` plus the adjacent Append policy tests at the same pinned project revision. Read `src/plan/existing.rs:210-270` and `src/plan/mod.rs:1030-1090`: Append compares the observed target base type with the planner's resolved `target_type`; this source `VARCHAR(64)` resolves to `varchar(64)`, so the independent target fixture must use the compatible `varchar(64)` declaration rather than widening it to `text`. Adaptation: make the fixture match the planner's declared mapping and drop its source table before recreating it, so a failed prior run cannot poison a retry. After this adjustment, the focused native T18 pipeline case passed both full Content and Append runs, including duplicate pre-existing rows, mode/status fields in persisted reports, and exact final table contents (1 passed, 0 failed); its owned fixture was stopped and removed. The complete serial lane is running again now.
