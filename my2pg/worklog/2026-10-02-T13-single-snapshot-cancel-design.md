## Coordinator correction after implementation

The first review described one source socket as the scheduler admission count
for schema-only/no-table SingleSnapshot runs. That understated the actual
preflight peak: the cancellation control session opens before catalog
inspection, while the selected plan is not yet known. The coordinator corrected
`Admission` to charge two source sockets for all SingleSnapshot preflights and
updated the architecture/checklist wording. No reference implementation in the
pinned corpus provides this preflight pattern; this is an application-specific
resource contract.

Independent review of the completed path also noted that cancellation before a
driver connection ID is exposed cannot be confirmed server-side. The pipeline
now leaves an initialization-uncertainty marker set through cancellation or
session-setup errors and reports that limitation without changing the exit
code. Required preflight/execution MDL cases pass, as does the refreshed full
MySQL 8.4/PostgreSQL 16 lane; broader shutdown/concurrency acceptance remains
open.

Primary sources checked against MySQL’s currently documented behavior:

- [MySQL 8.4 KILL statement](https://dev.mysql.com/doc/refman/8.4/en/kill.html), especially process-list IDs, the `CONNECTION`/`QUERY` distinction, same-account privileges, and asynchronous kill-flag completion. An account can kill its own threads without `CONNECTION_ADMIN`; the statement returns before the killed thread is confirmed dead. MySQL 5.7’s privilege documentation also says an account can kill its own threads and see its own process-list entries without `PROCESS` ([5.7 privileges](https://dev.mysql.com/doc/mysql-security-excerpt/5.7/en/privileges-provided.html)).
- [MySQL 8.4 metadata locking](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html), lines 516–534: metadata locks acquired by a transaction are held until transaction end, including locks for a syntactically valid statement that fails during execution. This makes `KILL QUERY` alone a poor cleanup contract for the snapshot transaction.
- [MySQL 8.4 consistent reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html): the repeatable-read view belongs to the original transaction. A replacement read connection cannot continue that snapshot.

## Design comparison

| Option | Snapshot / behavior | Connection and permission cost | Assessment |
| --- | --- | --- | --- |
| Drop the original reader socket or cancel its Rust future | Keeps normal reads on the original snapshot until cancellation, but the confirmed test shows that the blocked MySQL backend survives until external MDL is released. | No extra connection or privilege; it is the current behavior. | Insufficient. Socket close is not server-thread termination evidence. |
| Send `KILL QUERY` through a dedicated connection | Interrupts only the current SQL statement and leaves the MySQL session alive. This run is cancelled, so it would still need transaction rollback and reader teardown. The failed statement can retain transaction metadata locks until the transaction ends; statement selection also has a natural-completion race. | Requires a second connection; the same source account can kill its own thread. | Not the preferred operation. It adds cleanup steps without providing the strong session/transaction termination required here. |
| Pre-open a KILL-only control connection and send `KILL CONNECTION <reader_id>` | Leaves all actual catalog, table, and verification reads on one original snapshot reader. Cancelling the source session discards that transaction and releases its locks. Do not retry the SELECT or reconnect the reader. | Raises SingleSnapshot source-session use from 1 to 2, steady-state and peak. Reuses the configured MySQL URL, authentication, and TLS; no added grant is needed when control and reader authenticate as the same account. Account for both before target mutation. | Recommended. It is explicit, scoped to the exact connection owned by this migration, and matches the fact that cancellation terminates the whole run. |
| Set a short session `lock_wait_timeout` | Can bound some metadata-lock waits, but changes normal migration behavior: otherwise-valid reads fail when a lock lasts longer than the new limit. The setting applies per metadata-lock acquisition, not as a global run deadline; it does not prove cancellation of CPU-bound reads, socket stalls, or every command/phase. A failed statement can also keep transaction-held metadata locks until the transaction ends. | No added socket, but adds a session behavior/configuration contract; it is not currently in the source-session allowlist (`src/mysql/mod.rs:222-236`). | Not a replacement for cancellation. At most a separately reviewed operational policy, with explicit errors and tests. |
| Replace the SingleSnapshot reader or use one connection per table | A new connection has a different read view; reads across tables and content verification are no longer from the same transaction snapshot. | More reader sockets, not a KILL channel. | Reject: violates the consistency contract in `docs/architecture.md:82-89`. |

## Recommended ownership and lifecycle

Keep a single, stable source reader connection for all SingleSnapshot source reads. Open one additional source control connection with the same resolved source credentials and verified TLS before target mutation. The control connection must never run catalog/data/verification reads and must not begin the reader’s transaction. This preserves snapshot visibility while making the reader independently interruptible.

Register the exact reader `Conn::id()` before issuing the first source statement that can block, and retain that ID while the owned connection can still be executing. Cover preflight (including post-snapshot catalog recheck), table reads, content verification, and the transition into cleanup. Clear the ID only after ordinary reader completion/disconnect or after cancellation has been settled; never clear it just because the caller dropped a query future. Keep the original reader guard alive until its kill request and shutdown settlement finish.

On cancellation or a SingleSnapshot execution failure, issue `KILL CONNECTION <id>` over the independent control connection under the existing shared shutdown deadline. Numeric connection IDs are server-generated values from the owned connection, not configuration strings. Treat MySQL error 1094 (unknown/already-gone thread) as already terminated only after checking the exact ID is absent. MySQL documents that a successful KILL returns before thread exit; do not equate SQL acknowledgment with cleanup. Poll the control session’s own-account-visible `INFORMATION_SCHEMA.PROCESSLIST` entry for that ID until it disappears, using the same bounded deadline. Same-account thread visibility and own-thread termination avoid requiring `PROCESS` or `CONNECTION_ADMIN` on supported 5.7/8.0/8.4 lines. The native fixture’s independent observer should separately verify actual server-side disappearance while its external lock holder remains alive.

The run must not proceed to a replacement reader or claim the snapshot is preserved after kill. MySQL session death terminates the transaction, so all later source reads are cancelled. Existing PostgreSQL ACKs remain authoritative; do not replay batches or discard confirmed prefixes. If control connection creation, kill, or disappearance confirmation fails, close the client reader as fallback, report source-cancellation/shutdown evidence as failed or unconfirmed, and retain the original migration fault and ACK accounting. Never label cleanup confirmed on the basis of a dropped stream, `COM_QUIT` attempt, or successful KILL response alone.

## Resource and compatibility impact

`src/pipeline/scheduler.rs:187-214` currently reports `normal_source = 1` for SingleSnapshot and Frozen as active readers plus one source control connection. With an independently owned SingleSnapshot control connection, set the SingleSnapshot source bound to **two** for every non-schema-only run. The control session is steady-state, not an unbudgeted emergency socket; preserve schema-only’s zero table-reader admission while deciding whether control is opened only for modes that execute source work. Update the resource diagnostic (`src/pipeline/mod.rs:460-476,725`) and scheduler unit expectations (`src/pipeline/scheduler.rs:570-590`). If opening the second source session fails, fail preflight before any PostgreSQL mutation; do not silently fall back to the unbounded socket-drop behavior.

Update `docs/architecture.md:82-89` to describe one snapshot **reader** plus a shutdown-only source control connection, while making clear all snapshot reads still use one reader transaction. Update connection budget and shutdown wording in the scope, architecture, diagnostics, and acceptance docs. No user config switch is needed for this invariant. Do not request `PROCESS`, `CONNECTION_ADMIN`, `SUPER`, or an administrative listener; the controller targets only the connection created by the same authenticated source account. Verify own-thread process-list visibility and KILL behavior on all supported MySQL lines in native lanes before advertising the implementation as verified.
