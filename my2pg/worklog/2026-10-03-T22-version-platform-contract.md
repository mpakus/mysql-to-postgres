## Implementation and verification

The harness now owns a static exact inventory of the 157 ignored case IDs discovered on the native Darwin build at this source snapshot. `MYSQL_CASE_MANIFEST` contains a disposition for every inventory item in each of `mysql57`, `mysql80`, and `mysql84`. MySQL 5.7 has nine explicit `not_applicable` entries: the T05 metadata case requires invisible columns and enforced CHECK behavior; two T05 and two T10 label/metadata cases require recursive CTEs; T10 enum metadata reads `mysql.column_type_elements`; T12 required-DDL and T17 CHECK override require enforced source CHECK; and T17 functional-index override requires MySQL 8.0.13+. The other 148 MySQL 5.7 cases are explicit `pending`, and block full runs before `start()`; the harness does not turn this unknown status into a skip or pass. The full 8.0/8.4 inventory is currently dispositioned `run`. Unknown discovered IDs, duplicate IDs, missing manifest entries, malformed/unknown statuses, and reasonless `not_applicable` entries are errors. Reviewed non-applicable cases must map to a unique full Rust test ID before being passed to libtest `--skip`.

Pin input accepts the existing flat record, interpreted as a one-platform variant, or the nested schema `{"lane":{"platforms":{"linux/arm64":{...},"linux/amd64":{...}}}}`. Each nested record repeats the exact platform, kind, version prefix, image digest, tag provenance, and pin date. The matrix validates every variant and emits a row only for a MySQL/PostgreSQL pair sharing a platform; each row carries `mysql_pin_key`, `postgres_pin_key`, both full image digests, and `platform`. The runtime harness maps native `arm64`/`aarch64` or `amd64`/`x86_64` to the matching Linux platform, selects both pins by that key, and records them in connections metadata. The current flat ARM64 pins remain accepted. No registry/image/CI changes were made by this lease.
