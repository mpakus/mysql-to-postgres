Read the current originals: `src/postgres/observed_constraints.sql:1-90` retains all target constraint kinds and maps `conkey` attributes to ordered column names; `src/postgres/observed.rs:95-140` strictly decodes those observations into `TargetConstraintPart`; `src/model.rs:480-510` carries the kind, validation/deferral flags, ordinal and column name; and `src/plan/existing.rs:681-760` validates known `p/u/f/c/t` kinds and rejects any other kind. Read the two failing T13 runner setups at `src/pipeline/mod.rs:2250-2310`, which create the target schema, then switch the same tables to DataOnly+Append before invoking the real runner. Adjacent existing target-constraint tests in `tests/cases/t11_existing_policies.rs:590-675` assert malformed/unknown constraints remain blocked. These show the four new entries are exposed by PG18's changed catalog and hit the unknown-kind guard; the run log and release notes corroborate this inference.

The official PostgreSQL 18 release notes say column `NOT NULL` specifications are now stored in `pg_constraint` and can be marked `NOT VALID`; the official catalog docs identify `contype='n'` as a not-null constraint, while PostgreSQL 17 still represents relation not-null state in `pg_attribute`. PostgreSQL 18's CREATE TABLE docs say `NOT ENFORCED` currently applies only to CHECK and foreign-key constraints, not NOT NULL. Sources: [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html), [PostgreSQL 18 `pg_constraint`](https://www.postgresql.org/docs/18/catalog-pg-constraint.html), [PostgreSQL 17 `pg_constraint`](https://www.postgresql.org/docs/17/catalog-pg-constraint.html), and [PostgreSQL 18 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html). This is a target-catalog evolution, not a transfer-data incompatibility.

## Chosen adaptation and proof

Extend only the existing-constraint classifier to accept an observed PG18 `n` entry when it is a single-column, ordered, validated, non-deferrable NOT NULL constraint attached to a resolved target column that is itself planned non-null and positively observed non-null. Reject missing/multiple/unvalidated/deferrable/NO INHERIT or nullable-column mismatches; do not change the source plan, add a version-specific SQL branch, or treat unknown constraint kinds as harmless. `TargetColumnObserved.nullable` remains the structural cross-version truth; the new constraint entry must independently agree with it. Add a pure classifier regression for accepted and malformed `n` rows if the existing test seam permits it, then run the actual two previously failing T13 cases and the full MySQL 8.4 → PostgreSQL 18 lane, followed by MySQL 8.4 → PostgreSQL 16 to guard pre-18 catalogs.
