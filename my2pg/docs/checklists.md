# Completion checklists

Implementation items start unchecked. Record proof in a task worklog and link it before marking an item complete. A statement such as “implemented by design” is not a passing test result.

## Every task

- [ ] Read the task's specification, dependency artifacts, and applicable repository/skill instructions.
- [ ] Use the required `rtk` and `ponytail` workflow; record missing skill/tool limitations rather than claiming they ran.
- [ ] Before coding, [search XERJ references](reference-coding.md), read original source/tests, and record queries, pinned commits, file/line evidence, adaptation and acceptance tests in the task worklog.
- [ ] Claim exact file ownership and confirm dependencies are complete at the tested revision.
- [ ] Implement the smallest complete behavior within the MySQL-only scope.
- [ ] Add behavioral checks that fail for the relevant defect or missing behavior.
- [ ] Run appropriate formatting/lint/tests and record command, revision, environment, and result.
- [ ] Update any affected contract, config example, fixture manifest, and operator documentation.
- [ ] Record changed files, known limitations, and handoff details in a separate worklog entry.
- [ ] Have a peer/integrator review changes to shared contracts, migrations, recovery, or expected results.

T21 has deterministic profile scaling, a correctness-gated runner, and database-free tests. It selects seven fixed workloads: narrow integer, sparse/skewed unsigned-primary-key, four-large-table, eight-table relational, wide UTF-8/text/JSON/decimal, binary/large-row, and fixed-rate bad-text. The relational case forms a seven-edge parent/child chain and checks exact FK topology. The wide case records logical UTF-8/JSON/decimal payload bytes; the binary case moves 81,920-byte rows containing NUL/high-bit bytes and checks large-payload length/content fingerprints plus exact nullable, empty, and non-empty VARBINARY states.
