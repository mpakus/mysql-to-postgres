# Tests and performance

## Evidence model

Use three distinct oracles:

1. **The my2pg contract:** reviewed expected target values and structures, including intentional differences from pgloader.
2. **Differential baselines:** the pinned v3 and v4 implementations on the same supported fixture, with differences classified explicitly.
3. **Independent database assertions:** inspect PostgreSQL catalogs and actual data, then exercise constraints/defaults/identities through writes in disposable test databases.

A green snapshot of generated SQL is insufficient. A green count check is insufficient for content equivalence. An expected file regenerated by the implementation under test is not independent evidence.

Property tests should concentrate on COPY escape/round trips, identifier quoting/name allocation, enum/array escaping, and range coverage. Fuzz the TOML/legacy parser and row encoders with bounded input sizes. Preserve discovered failures as small deterministic regression cases. Do not replace real transaction tests with mock call-count assertions.

## Test harness and CI

Create a Rust integration harness and a small Docker Compose setup for disposable MySQL/PostgreSQL services. Give each agent/run a unique Compose project, database, and artifact path. Bind local test ports to loopback or use a private container network. Seed deterministic data; wait for health checks; teardown only that run's resources. A missing database in an explicitly requested integration lane is a failure, not a successful skip.

| Lane | Required coverage |
| --- | --- |
| Every PR, no database | Format, Clippy, automatically discovered unit tests, config/examples, CLI snapshots, property regressions |
| Every PR, database | MySQL 8.4 → PostgreSQL 16; complete core migration/recovery/failure suite; MySQL 8.0 → PostgreSQL 18 representative compatibility suite |
| Scheduled or pre-release | Full MySQL 5.7/8.0/8.4 × PostgreSQL 16/17/18 matrix; pinned images/digests and recorded architecture |
| Optional PostGIS feature | Supported PostgreSQL/PostGIS pair with geometry/SRID round trips; missing-extension negative test against plain PostgreSQL |
| Fault/soak | Large rows, slow destination, intermittent transport, cancellation, bounded RSS trend, filesystem failures |

For the T13 repeated-stability soak, use one owned fixture and one unchanged executable on the same host and pinned MySQL/PostgreSQL pair. Run the complete `t13_concurrency` target serially at least 24 times and for at least 60 minutes of measured target runtime. Every cycle must pass all 11 registered cases; the fixed-budget RSS case must retain its exact row/report checks, keep peak source and target connections at or below 3, and keep the 20,000-to-200,000-row/table RSS increase at or below 1 MiB. Preserve each cycle's raw log and RSS artifact. This threshold qualifies repeat-stability evidence for that host/pair only; it does not replace slow-destination, other transport/filesystem fault cases, or the cross-platform T22 gates. The 2026-10-05 ARM64 MySQL 8.4/PostgreSQL 16 sample met these repeat-stability thresholds; see the [soak result](../worklog/2026-10-05-T22-prolonged-soak-result.md). The broader T22 fault and platform gate remains open.
| Bench host | Repeated comparable timing/RSS runs after correctness checks |
| Packaging | Linux x86_64/aarch64 and macOS arm64 smoke; additional platforms only when tested |

MySQL 5.7 test images may require x86_64 execution. Use a native x86_64 CI lane rather than reporting emulation timings as performance evidence. Pin the selected image digests during T02/T22. Never weaken 8.4 authentication to make the new Rust implementation work like the old v3 harness.

Proposed commands, to be made real by T01/T02:

```sh
rtk cargo fmt --all -- --check
rtk cargo clippy --locked --all-targets --all-features -- -D warnings
rtk cargo test --locked --all-targets --all-features -- --test-threads=1
rtk run './tests/run-integration.sh mysql84 pg16'
rtk run './tests/run-integration.sh mysql80 pg18'
```

The integration script owns startup, readiness, explicit database-test execution, artifact capture, and scoped cleanup. Unit discovery must not maintain a handpicked list of test modules. Keep the ordinary Rust test threads serial: several production-writer tests share one process-global artifact-worker slot. Required database tests may be separate from ordinary `cargo test`, but the CI lane must show their case counts and failures. Cargo/toolchain installation is implementation setup, not something performed by this planning pass.

Database cases within an owned fixture run with `--test-threads=1` because event-trigger DDL is global to that database. Separate worker fixtures may still run concurrently. Native macOS durability cases use uniquely owned64MiB disk images and retained ownership/errno evidence; platform-specific tests do not count as Linux coverage. Descriptor-induced fsync EINVAL is distinct from physical storage-sync failure.

The separately pinned `pg16-nls` Debian ARM64 lane proves real translated builtin errors. Start that owned lane, generate/verify its locale only inside its container, then run `bin/cargo test --locked --features nls-integration --test nls -- --ignored --nocapture` with `MY2PG_NLS_LOCALE` and its connection environment. Missing locale fails. The default Alpine lane lacks NLS and does not discover this feature-required test target. [Exact lifecycle, locale and SQLSTATE evidence](../worklog/2026-10-01-T12-durable-faults.md).

The documents' code/config examples become executable fixtures as features land. Parser validation, relative links, task IDs, and status consistency are documentation checks. Required Rust checks run on touched behavior first; full matrix repetition is reserved for changes that affect it and release gates.

## Reconciliation

For each successful full migration, verify selected table/column/key definitions, nullability/default decisions, index/check/FK presence **and validity**, sequence ownership and next-value lower bound, and source-read/committed/rejected accounting. Compare exact row counts against the same source snapshot when available; source catalog estimates are only progress hints.

Content mode compares canonical values under the resolved mapping, including duplicate counts for keyless tables. Use complete scanning and bounded/external storage. The source-side expected data and the target-side comparison need independent test oracles: sharing an encoder must not allow the same corruption to pass both sides unnoticed. Report intentional transformations by column and count; distinguish byte equality from JSON or floating-point semantic comparison.

Store machine-readable results with source/target versions, fixture ID/digest, plan/config digest, binary revision, selected policy, failed case IDs, and artifact hashes. Keep real production data and raw credentials out of committed fixtures and CI artifacts.

## Proving faster

The pgloader v4 adapter builds the pinned, clean source revision with the attributed out-of-tree patch at `tests/performance/patches/pgloader-t21-phase-intervals.patch`. The patch adds run-relative monotonic catalog, COPY, and index/constraint intervals to the native JSON summary. It also converts the pinned parser's nested batch-size value to the byte-count string expected by pgloader's runtime; the image build runs the adjacent summary and load-file parser suites. The adapter renders `batch rows`, `batch size`, and `prefetch rows` from the declared comparison settings. COPY and index/constraint intervals intentionally overlap. The runner adds its measured source-plus-target verification interval and accepts normalized comparison only when all four phases and operation classes pass the same strict validation used for My2pg. A live correctness-only smoke passed for both loaders with all four phases supported and exact row-content reconciliation. That validates instrumentation and correctness, not performance: randomized row capacity, one-row byte-cap overflow, and other memory and row-error policy gaps remain, as do repeated timing, multi-GiB memory, and idle-host gates. The original reference checkout and published image are not modified; each artifact records source revision, runtime image ID, and patch digest.

The pinned pgloader v4 normally strips embedded NULs, so the T21 adapter adds a workload-specific CAST rule for the synthetic payload column to bypass that default transform. On MySQL 8.4.11/PostgreSQL 16.15, correctness-only smokes passed for both loaders at 0.1%, 1%, and 5%: they accepted 999/990/950 rows and matched the same 1/10/50 rejected IDs and raw payload bytes. No timing was collected.

The T21 runner also supports `--correctness-only`. Use it with a small profile and an owned disposable fixture to run each configured loader once through the same independent target-content and reject checks, without collecting benchmark iterations. Its artifacts are explicitly labeled correctness-only and never eligible for timing claims. For `bad_rows_fixed_rate`, the gate compares exact reject IDs and raw payload bytes against MySQL; pgloader's workload-specific CAST override preserves NULs so PostgreSQL rejects the same rows. Live MySQL 8.4.11/PostgreSQL 16.15 smokes passed for both loaders at 0.1%, 1%, and 5%, matching the exact rejected IDs/payload bytes and accepted-row streams. This is functional evidence only. `--prepare-only` remains the source-seed/oracle path when no loader invocation is wanted.

The seven T21 workload classes pass live correctness-only comparisons at smoke and small profiles on MySQL 8.4.11/PostgreSQL 16.15. Six also pass at medium profile. The 10-million-row narrow-integer large profile now passes on both loaders with matching independent source/target row digests, aggregates, schema and primary key. The original attempt completed pgloader COPY but PostgreSQL killed its target-oracle backend with signal 9 under the fixture's 512 MiB limit; the cause is unknown. The successful correctness-only retry raised only PostgreSQL's fixture cap to 2 GiB while keeping each loader at 512 MiB, so it is neither matched-resource nor timing evidence. See the [large-profile failure reconciliation](../worklog/2026-10-05-T21-large-oracle-failure-reconciliation.md) and [successful large-profile retry](../worklog/2026-10-05-T21-large-profile-retry.md). The 5,000-row binary medium profile passed on 2026-10-03: both loaders matched the independent correctness gate across 409,648,000 payload bytes under the declared 1 CPU/512 MiB loader limits. This closes medium binary correctness only; its sampled container memory and recorded durations are not accepted as comparable peak RSS or timing evidence. See the [binary medium correctness worklog](../worklog/2026-10-03-T21-binary-medium-correctness.md). For the fixed-rate reject workload, 0.1%, 1%, and 5% smoke cases and the 1% small and medium cases pass the exact accepted-content and durable reject-receipt checks. The wide-row oracle uses binary concatenation and lowercase HEX so MySQL collation and case differences do not alter its digest. The binary workload uses a scoped pgloader `hex-to-bytea` CAST for the seeded LONGBLOB and VARBINARY columns; without it, pinned v4's default transform doubled the byte count. All of this is correctness evidence, not timing acceptance.

First capture v3 and v4 at the audited revision in an isolated, reproducible environment. A loader that fails correctness on a fixture is not a performance baseline for that fixture. The existing employees benchmark uses a MariaDB source setup, while other benchmark cases use SQLite/CSV; re-seed suitable data into actual MySQL or build a synthetic MySQL case. Do not count those existing runs as evidence for a MySQL-only product.

Use a declared corpus, fixed before optimization:

| Workload | What it exposes |
| --- | --- |
| Many small relational tables | Startup, introspection, DDL, indexes/FKs |
| One large narrow integer table | COPY and source throughput |
| Several large tables | Table concurrency and resource limits |
| Wide UTF-8/text/JSON/decimal rows | Conversion cost, allocations, exactness |
| Binary/large-row data | Byte budget, expansion, driver packet memory |
| Bad-row dataset at fixed error rates | Recovery cost and reject durability |
| Sparse/skewed unsigned PKs | Range overhead and scheduling correctness |

Include fixed-seed scales from quick smoke data up to multi-GiB data exceeding the memory budget. Record row counts and digests, not only generator arguments. Pin CPU/memory limits, storage, DB settings, network, TLS, source/target versions, Rust release flags, and JVM heap. Use the same durability, mapping, indexes, error policy, and concurrency limits for comparable runs. Label single-reader and parallel results separately.

Measure process startup and total wall time from process launch to finalized report. Also measure catalog, COPY, index/constraint, and verification phases separately; peak process/container RSS; CPU time; rows/s; encoded MiB/s; queue wait; retries; and source/target load. Verification cost must be equal across compared runs or broken out explicitly. Never disable fsync, constraints, TLS, or required validation only for the Rust contender.

The normalized event format is one JSON object per phase with `kind = "phase_interval"`, canonical `phase`, `clock = "run_monotonic_millis"`, `scope = "run"`, integer `start_elapsed_millis` and `end_elapsed_millis`, and `operation_classes`. Each canonical phase must occur exactly once. Its operation classes are fixed: catalog (`source_mysql_catalog`, `target_postgresql_schema_table_prepare`), copy (`row_copy`), index/constraints (`primary_keys`, `indexes`, `foreign_keys`, `check_constraints`), and verification (`mysql_source_oracle`, `postgresql_target_oracle`). My2pg's catalog interval runs from its first MySQL/PostgreSQL catalog inspection through target prepare DDL; it includes plan revalidation, safety/baseline checks, artifact initialization and pre-load hooks between those endpoints. Its run-wide COPY interval spans the earliest through latest table/range transfer-pipeline boundary, while table-local durations remain diagnostics. Its index/constraint interval spans finalization DDL through PK/index/FK/check completion and ends before sequence handling. The runner reruns the independent MySQL source oracle and PostgreSQL target oracle after every successful loader call, comparing both against the seed oracle. It preserves that measured verification duration and positions the interval after the latest migration interval in the normalized run timeline; no gap or disjoint total is inferred from the normalized ordering. COPY and index/constraint intervals may overlap and are measured independently. Missing, duplicate, malformed, table-scoped, or incompatible intervals make phase metrics unsupported. Existing point markers and loader-native aggregate totals do not establish this contract.

Use a dedicated benchmark host or schedule database stress tests outside measurement windows. Agents may work on code or reports in parallel, but running the version matrix beside a benchmark on the same constrained machine invalidates a comparable timing run.

Use at least one warm-up and five measured runs in randomized tool order. Record median, spread, and warm/cold cache policy. Check correctness for every measured run. Shared CI timing is informational; use a stable host for acceptance.

Proposed performance acceptance targets:

- At least **1.25× geometric-mean end-to-end speedup** against the fastest correct pgloader baseline on the predeclared large-data subset.
- No unexplained median regression above **10%** on another designated workload.
- At fixed settings, increasing dataset size tenfold does not cause retained batch memory to grow with total rows; explain measured driver/RSS overhead.
- Aim for at least **30% lower peak RSS than v4** on the large-data subset; report actual v3 comparison separately.

These are targets, not observations. If missed, profile allocations, encoding, COPY round trips, source queries, and index scheduling. Optimize the demonstrated bottleneck. A correct release can be proposed with amended scope, but it cannot be described as meeting the user's speed goal without the evidence or an explicit revised target.

Binary COPY, SIMD/custom parsers, multi-crate partitioning, and automatic resume are future experiments only after a benchmark or real operational need justifies their cost.
